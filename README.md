# Polar Penguin

Google Drive의 `Input`을 감시해 주문·재고 파일을 자동 처리하고 `Output`에 피킹 PDF를 만드는 Google Apps Script 창고 워크플로입니다.

## 운영 흐름

일반 주문은 유형 판별과 검증, 주문 취입, 주문 전체 재고 예약, 피킹 데이터 생성, PDF 출력까지 자동 처리됩니다. PDF가 생성되어 창고에서 사용할 수 있게 된 첫 시점에 fulfillment가 확정됩니다. 시스템은 `예약재고`만 소진하고 피킹 라인에 `확인=O`, `실제수량=필요수량`, `라인상태=완료`, 처리일시를 기록한 뒤 헤더와 주문을 `완료`/`출고완료`로 바꿉니다. 원본은 이 전 과정이 성공한 뒤에만 `Success/YYYY-MM-DD`로 이동합니다.

S3 예약 시 재고는 `가용 → 예약`으로 한 번 이동합니다. 예를 들어 가용 100에서 10개를 주문하면 예약 후 가용 90/예약 10, PDF 성공 후 가용 90/예약 0입니다. 출력 확정은 가용재고를 다시 줄이지 않습니다.

재고 부족 또는 예약상품이 포함된 주문은 `예약` 상태로 유지됩니다. `예약상품 피킹 관리`에서 상품을 고르면 시스템이 주문일시·주문번호·품목별 주문번호 순 FIFO와 주문 전체 SKU 재고를 계산합니다. 선택된 주문만 가용재고를 예약한 뒤 같은 PDF 출력/finalizer 경로로 `출고완료`가 되며, 선택되지 않은 주문은 `예약`으로 남습니다. 같은 주문번호에 일반상품과 예약상품이 섞이면 부분 출고하지 않습니다. 서로 다른 주문번호의 일반 주문은 동일 고객의 예약 주문과 독립적으로 출고됩니다.

지속 주문 상태는 다음 세 가지입니다.

- `예약`: 아직 출력 확정되지 않은 유효 주문
- `출고완료`: 피킹 출력이 성공하고 예약재고 소진이 끝난 주문
- `취소`: 주문 단위 취소와 필요한 재고 복원이 끝난 주문

## 피킹지시서

정상 주문과 예약 FIFO 배치는 하나의 문서 모델을 사용합니다. A4 가로형 PDF의 `창고 피킹 요약`은 피킹지시 전체 품목을 SKU별로 합산해 보관위치, 상품, 옵션, 주문 건수, 총수량을 보여 줍니다. 같은 SKU가 73개 주문에 걸쳐 총 100개라면 한 행에 `주문 73건 · 총 100개`로 표시됩니다. `주문별 포장 / 송장 확인`은 주문일시와 주문번호 순으로 수령인, 휴대전화 마지막 4자리, 우편번호, 품목 배분을 보여 줍니다.

카트 슬롯과 작업자 배정은 창고의 물리적 선택이므로 입력이나 출력 조건이 아닙니다. 위치가 비어 있는 SKU는 PDF에서 `⚠ (위치 미지정)`으로 남고, 메뉴의 위치 관리 화면에서 여러 상품의 `기본보관위치`를 한 번에 저장할 수 있습니다. 이 필드는 창고 소유 정보이므로 Cafe24 재고 동기화가 덮어쓰지 않습니다.

## 출력 실패, 재시도, 재출력

PDF 생성에 실패하면 예약재고를 소진하지 않고 헤더를 `출력오류`로 남깁니다. `피킹지시서 조회 / 재출력`에서 같은 피킹지시번호를 재시도하면 기존 예약과 피킹 행을 재사용하고, 성공 시 공용 `finalizePickingAfterOutput_`가 한 번만 출고를 확정합니다.

이미 완료된 지시의 재출력은 문서만 준비합니다. 주문/라인 상태가 idempotency 표식이므로 재고 이동이나 출고 로그를 중복 생성하지 않습니다. 브라우저가 실제 프린터 완료를 확인할 수 없으므로, PDF 파일 또는 인쇄 가능한 화면이 성공적으로 준비된 시점을 출력 성공으로 봅니다.

## 취소

문제는 `선택 주문 취소`로 처리하며 모든 호출은 `cancelOrder_` 한 경로를 사용합니다. 출력 전 예약 주문은 `예약재고 → 가용재고`로 되돌리고, 출력 후 `출고완료` 주문은 실제 출고수량을 가용재고에 복원합니다. 출력 후 취소에는 명시적 경고와 확인이 필요합니다. 이미 취소된 주문은 두 번째 호출에서도 재고를 다시 복원하지 않습니다.

## 백업, 보존기간, 알림

`⚙ 관리 → 백업 및 정리`는 현재 운영 Spreadsheet 전체를 native Google Spreadsheet로 `Backup/YYYY-MM/Polar Penguin Backup YYYY-MM-DD HHmmss`에 복사합니다. 복사본 ID, 접근 가능 여부, 대상 폴더, 필수 탭을 모두 검증한 뒤에만 정리를 시작합니다. 백업이나 사전 점검이 실패하면 주문·피킹·Drive 파일을 하나도 삭제하지 않습니다.

기본 `정리보존일수`는 30일입니다. 그보다 오래되고 신뢰할 수 있는 최종시각이 있는 `출고완료`·`취소` 주문만 정리하며, `예약`, `출력오류`, 중간/알 수 없는 상태는 보존합니다. 정리 전에 `품목별 주문번호`와 최소 상품/상태 정보가 숨김 탭 `처리주문아카이브`에 저장됩니다. 이 탭은 재수입 중복 방지용 경량 색인이고, 전체 복구 자료는 Backup의 Spreadsheet 사본입니다. 고객 주소·전화·배송메시지는 아카이브하지 않습니다.

Success, Error, 안전하게 종료된 Output PDF는 보존기간이 지나면 Drive 휴지통으로 이동합니다. Input과 Backup은 자동 정리하지 않습니다. 공유 피킹 배치는 관련 주문이 모두 운영 데이터에서 빠진 뒤에만 정리됩니다.

`알림이메일`을 설정하면 Input 실패, PDF/예약 피킹 실패, 취소 실패, 백업 실패와 유지보수 결과가 중앙 Gmail 알림으로 발송됩니다. 백업/정리 성공 메일에는 첨부파일 대신 복구용 Drive 링크와 단계별 정리 건수가 포함됩니다. 이메일 미설정이나 Gmail quota 오류는 업무 처리를 되돌리지 않으며 작업로그와 시스템 상태에 경고로 남습니다.

## 운영자 화면과 메뉴

`피킹(라인)`은 시스템 관리 이력/감사 시트입니다. `확인` 열은 호환성을 위해 남아 있지만 출력 성공 시 시스템이 O를 기록하며 운영자가 편집하지 않습니다.

- `📥 Input` → `Input 지금 처리`
- `📋 주문` → `선택 주문 취소`, `예약상품 피킹 관리`
- `📄 피킹지시서` → `피킹지시서 조회 / 재출력`
- `📍 위치 관리` → `위치 미지정 상품`
- `📊 운영` → `대시보드 갱신`, `시스템 상태 확인`
- `⚙ 관리` → `시스템 설치 / 복구`, `백업 및 정리`, `로그 정리`

필요 트리거는 `processInput`과 `onOpen`입니다. 대시보드는 각 mutation 경로에서 직접 갱신됩니다. S1~S4와 이전 S5 호환 함수는 운영 메뉴에 노출하지 않습니다.

## 설치와 검증

`setRootFolder(folderUrlOrId)` 후 `setupSystem()`을 실행합니다. 재실행은 기존 데이터와 사용자 설정을 보존하면서 누락 리소스, 서식, validation, 트리거를 복구합니다.

```sh
npm test
npm run lint
git diff --check
clasp status
```

`clasp push` 전에는 반드시 `clasp status`에서 `src/` 아래 파일만 표시되는지 확인합니다.
