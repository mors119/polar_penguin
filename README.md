# Polar Penguin

Google Drive의 `Input`을 감시해 주문·재고 파일을 자동 처리하고 `Output`에 피킹 PDF를 만드는 Google Apps Script 창고 워크플로입니다.

## 운영 흐름

일반 주문은 유형 판별과 검증, 주문 취입, 주문 전체 재고 확정, 피킹 데이터 생성, PDF 출력까지 자동 처리됩니다. S3에서 주문 수량을 `가용재고`에 한 번만 반영하고 `확정일시`를 idempotency 표식으로 남깁니다. PDF가 성공하면 재고를 다시 차감하지 않고 피킹 라인에 `확인=O`, `실제수량=필요수량`, `라인상태=완료`, 처리일시를 기록한 뒤 헤더와 주문을 `완료`/`출고완료`로 바꿉니다. 원본은 이 전 과정이 성공한 뒤에만 `Success/YYYY-MM-DD`로 이동합니다.

상품마스터의 핵심 재고 필드는 `가용재고`와 `재고관리`입니다. `가용재고`는 현재 순 재고 위치입니다. `재고관리=T`는 기존 재고 부족 대기 행동을 유지하고, `재고관리=F`는 주문 수요가 가용재고를 0 아래로 자연스럽게 내릴 수 있습니다. 예를 들어 물리 재고 0개에 미충족 수요 50개면 -50, 물리 재고 40개에 수요 50개면 -10, 물리 재고 60개에 수요 50개면 +10입니다.

재고 부족으로 대기하는 주문은 `예약` 상태로 유지됩니다. `예약상품 입고 관리`는 `재고관리=F` 상품의 Input 파일 없는 실물 입고를 delta로 등록하는 예외 경로입니다. 대기 주문 수와 대기 수량을 구분해서 보여 주며, `주문상태=예약`이고 피킹지시번호가 없는 실제 주문 행을 FIFO 후보로 사용합니다. 원본에 주문일시 계열 열이 있으면 주문일시·주문번호·품목별 주문번호 순 FIFO를 사용하고, 없으면 기존의 결정적 주문번호/품목번호 fallback을 사용합니다. 선택되지 않은 주문은 `예약`으로 남습니다.

음수 가용재고는 미충족 수요가 있다는 순 재고 표현이지 출고완료를 뜻하지 않습니다. 어느 주문이 예약·피킹중·출고완료·취소인지는 주문과 피킹 테이블의 상태가 결정합니다. Cafe24 `재고수량`은 가산 입고량이 아닌 물리 재고 snapshot으로 유지되며, 현재 확정되었지만 출고완료되지 않은 수요를 빼 순 재고를 재계산합니다. 같은 snapshot을 반복 처리해도 누적하지 않습니다.

F 상품의 수동 입고는 현재 순 재고에 한 번만 더합니다. FIFO release는 최종 순 재고가 0 이상인지 보지 않고, `순 가용재고 + 아직 피킹지시가 없는 확정 예약 수요`로 파생한 기존 미사용 물리 재고와 새 입고를 사용합니다. 가장 오래된 주문을 완전히 충족하지 못하면 해당 SKU 큐를 멈추며, 남은 물리 재고는 다음 입고 때 다시 합산됩니다. 주문 수요는 S3에서 이미 차감되었으므로 예약 피킹과 PDF 출력은 재고를 다시 차감하지 않습니다. 정상 Inventory Input 자동 release를 연결할 때는 S1 snapshot 반영 뒤 공용 `releaseReservationQueue_`를 호출합니다.

지속 주문 상태는 다음 세 가지입니다.

- `예약`: 아직 출력 확정되지 않은 유효 주문
- `출고완료`: 피킹 출력과 상태 확정이 끝난 주문
- `취소`: 주문 단위 취소와 필요한 재고 복원이 끝난 주문

## 주문 시트 스키마

`주문(완료)`의 앞부분은 항상 다음 25개 고정 열을 같은 순서로 유지합니다.

`쇼핑몰`, `쇼핑몰번호`, `주문번호`, `품목별 주문번호`, `배송메시지`, `총 주문금액(KRW)`, `총 결제금액(KRW)`, `상품품목코드`, `주문상품명(기본)`, `상품옵션(기본)`, `수량`, `판매가`, `수령인`, `수령인 휴대전화`, `수령인 우편번호`, `수령인 주소(전체)`, `출고완료`, `피킹지시번호`, `주문상태`, `취소사유`, `취소일시`, `취소경로`, `확정일시`, `대기사유`, `운영메모`

그 뒤에는 실제로 취입한 CSV/Google Spreadsheet에서 관찰된 추가 열만 붙습니다. 예를 들어 `주문일시`나 `배송업체`가 원본에 있을 때만 동적 열로 추가되며, 다음 파일에 없더라도 이미 수집한 동적 열과 데이터는 보존됩니다. `상품명`, `옵션명`, `수령인 주소` 같은 이전 중복 열은 각각 `주문상품명(기본)`, `상품옵션(기본)`, `수령인 주소(전체)`로 안전하게 흡수됩니다. 정식 값이 이미 있으면 레거시 값으로 덮어쓰지 않습니다.

## 피킹지시서

정상 주문과 예약 FIFO 배치는 하나의 문서 모델을 사용합니다. A4 가로형 PDF의 `창고 피킹 요약`은 피킹지시 전체 품목을 SKU별로 합산해 보관위치, 상품, 옵션, 주문 건수, 총수량을 보여 줍니다. 같은 SKU가 73개 주문에 걸쳐 총 100개라면 한 행에 `주문 73건 · 총 100개`로 표시됩니다. `주문별 포장 / 송장 확인`은 주문일시와 주문번호 순으로 수령인, 휴대전화 마지막 4자리, 우편번호, 품목 배분을 보여 줍니다.

카트 슬롯과 작업자 배정은 창고의 물리적 선택이므로 입력이나 출력 조건이 아닙니다. 위치가 비어 있는 SKU는 PDF에서 `⚠ (위치 미지정)`으로 남고, 메뉴의 위치 관리 화면에서 여러 상품의 `기본보관위치`를 한 번에 저장할 수 있습니다. 이 필드는 창고 소유 정보이므로 Cafe24 재고 동기화가 덮어쓰지 않습니다.

## 출력 실패, 재시도, 재출력

PDF 생성에 실패하면 S3에서 이미 한 재고 확정을 유지하고 헤더를 `출력오류`로 남깁니다. `피킹지시서 조회 / 재출력`에서 같은 피킹지시번호를 재시도하면 기존 피킹 행을 재사용하고, 성공 시 공용 `finalizePickingAfterOutput_`가 재고를 다시 차감하지 않고 한 번만 출고를 확정합니다.

이미 완료된 지시의 재출력은 문서만 준비합니다. 주문/라인 상태가 idempotency 표식이므로 재고 이동이나 출고 로그를 중복 생성하지 않습니다. 브라우저가 실제 프린터 완료를 확인할 수 없으므로, PDF 파일 또는 인쇄 가능한 화면이 성공적으로 준비된 시점을 출력 성공으로 봅니다.

## 취소

문제는 `선택 주문 취소`로 처리하며 모든 호출은 `cancelOrder_` 한 경로를 사용합니다. 출력 전에는 `확정일시`가 있어 이미 가용재고에 반영된 주문만 정확한 수량을 복원합니다. `출고완료` 주문은 피킹 라인의 실제 출고수량을 가용재고에 복원합니다. 출력 후 취소에는 명시적 경고와 확인이 필요하고, 이미 취소된 주문은 두 번째 호출에서 재고를 다시 복원하지 않습니다.

## 백업, 보존기간, 알림

`⚙ 관리 → 백업 및 정리`는 현재 운영 Spreadsheet 전체를 native Google Spreadsheet로 `Backup/YYYY-MM/Polar Penguin Backup YYYY-MM-DD HHmmss`에 복사합니다. 복사본 ID, 접근 가능 여부, 대상 폴더, 필수 탭을 모두 검증한 뒤에만 정리를 시작합니다. 백업이나 사전 점검이 실패하면 주문·피킹·Drive 파일을 하나도 삭제하지 않습니다.

기본 `정리보존일수`는 30일입니다. 그보다 오래되고 신뢰할 수 있는 최종시각이 있는 `출고완료`·`취소` 주문만 정리하며, `예약`, `출력오류`, 중간/알 수 없는 상태는 보존합니다. 정리 전에 `품목별 주문번호`와 최소 상품/상태 정보가 숨김 탭 `처리주문아카이브`에 저장됩니다. 이 탭은 재수입 중복 방지용 경량 색인이고, 전체 복구 자료는 Backup의 Spreadsheet 사본입니다. 고객 주소·전화·배송메시지는 아카이브하지 않습니다.

Success, Error, 안전하게 종료된 Output PDF는 보존기간이 지나면 Drive 휴지통으로 이동합니다. Input과 Backup은 자동 정리하지 않습니다. 공유 피킹 배치는 관련 주문이 모두 운영 데이터에서 빠진 뒤에만 정리됩니다.

`알림이메일`을 설정하면 Input 실패, PDF/예약 피킹 실패, 취소 실패, 백업 실패와 유지보수 결과가 중앙 Gmail 알림으로 발송됩니다. 백업/정리 성공 메일에는 첨부파일 대신 복구용 Drive 링크와 단계별 정리 건수가 포함됩니다. 이메일 미설정이나 Gmail quota 오류는 업무 처리를 되돌리지 않으며 작업로그와 시스템 상태에 경고로 남습니다.

## 운영자 화면과 메뉴

`피킹(라인)`은 시스템 관리 이력/감사 시트입니다. `확인` 열은 호환성을 위해 남아 있지만 출력 성공 시 시스템이 O를 기록하며 운영자가 편집하지 않습니다.

- `📥 Input` → `Input 지금 처리`
- `📋 주문` → `선택 주문 취소`, `예약상품 입고 관리`
- `📄 피킹지시서` → `피킹지시서 조회 / 재출력`
- `📍 위치 관리` → `위치 미지정 상품`
- `📊 운영` → `대시보드 갱신`, `시스템 상태 확인`
- `⚙ 관리` → `시스템 설치 / 복구`, `백업 및 정리`, `로그 정리`

필요 트리거는 `processInput`과 `onOpen`입니다. 대시보드는 각 mutation 경로에서 직접 갱신됩니다. S1~S4와 이전 S5 호환 함수는 운영 메뉴에 노출하지 않습니다.

## 설치와 검증

`setRootFolder(folderUrlOrId)` 후 `setupSystem()`을 실행합니다. 재실행은 기존 데이터와 사용자 설정을 보존하면서 누락 리소스, 서식, validation, 트리거를 복구합니다. 기존 이중 재고 스키마를 처음 이전할 때는 이미 주문 수요가 차감된 기존 `가용재고`를 그대로 보존하고 레거시 열을 헤더 이름으로 오른쪽부터 제거합니다. 따라서 기존 확정 수요를 버리거나 두 번 차감하지 않으며, 재실행해도 같은 스키마를 유지합니다.

```sh
npm test
npm run lint
git diff --check
clasp status
```

`clasp push` 전에는 반드시 `clasp status`에서 `src/` 아래 파일만 표시되는지 확인합니다.
